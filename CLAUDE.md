# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

The maintainer may converse in Italian or English, but all code, comments, commit messages, and documentation must be written in English.

## What this is

"Draftham Horror" — a client-side drafting tool for *Arkham Horror: The Card Game* (a fork of Skeezix55/ArkhamDraft). Users pick a collection, an investigator and draft rules, then the app randomly drafts a deck (build) and/or upgrades (spend XP) using card data fetched live from the ArkhamDB public API. Plain JavaScript (no TypeScript), Vite 5, React 18, Redux Toolkit. No backend.

## Commands

The app is built with Vite (`vite.config.js`); the app root is `src/` (its `index.html` is the entry, static files come from `public/`).

- `npm start` — dev server on http://localhost:3000
- `npm run build` — production build into `build/` (gitignored; the build empties that folder first). To check that it compiles without touching `build/`, pass another folder: `npm run build -- --outDir <dir> --emptyOutDir`.
- `npm run preview` — serves the production build
- `npm test` — Vitest (jsdom); the only tests are the interface-text checks in `src/i18n/locales.test.js`
- `npm run lint` — ESLint with the `react-app` config (unused variables and imports, hooks rules); run it before finishing a change, there is no lint step in the dev server or the build
- `npm run deploy` — `predeploy` builds, then `gh-pages -d build` publishes it to the `gh-pages` branch, which GitHub Pages serves at https://radghiv.github.io/DrafthamHorror/

The sources use JSX in `.js` files, so `vite.config.js` tells esbuild and the React plugin to read `.js` as JSX.

## Hosting

The site is served by GitHub Pages from the `gh-pages` branch (Settings → Pages → *Deploy from a branch*); `main` holds only the sources. The build uses relative paths (`base: './'`), so it works under `/DrafthamHorror/` and on a custom domain. `package.json` `homepage` is informational.

## Architecture

**Data flow:** `src/index.js` applies the stored theme (`theme.js`) and dispatches the thunks `fetchCards`, `fetchTaboo` and `fetchPacks` (in `features/data/dataSlice.js`) on startup, which pull the full card DB, the taboo list and the pack list from `arkhamdb.com/api/public/*` into the `data` slice. Everything else is derived from that raw ArkhamDB card JSON (fields like `deck_options`, `deck_requirements`, `faction_code`, `xp`, `real_name`, `pack_code`). Deck import also hits ArkhamDB (`fetchDeck`, validated and loaded by `applyDeck`/`validateDeck`/`loadDeckCards`).

**Redux store (`src/store.js`)** — four slices in `src/features/`:
- `settings` — all user choices (investigator and how it is chosen, classes, draft type/weighting/counts, selected taboo, ban list, upgrade options, animation and layout preferences, current wizard step, `drafting`/`complete` flags). Exposes `reset` (listened to by other slices), `changeSetting`, and the `calculateFilteredCount` thunk. `investigatorActions.js` holds the investigator thunks (selecting an entry, drawing and redrawing the investigator pool, picking one).
- `data` — raw card/taboo/pack data, fetch/loading flags, taboo merging (`mergeTabooData`), imported-deck state, `syncCollectionPacks`.
- `draft` — the in-progress draft: `deckList`, `cardList`, `removedList`, draft pool (cards are revealed one by one), per-phase progress, deck modifiers, exile/burn state. Also holds the draft-lifecycle thunks `startDraft`, `advanceDraft`, `updateDeckRequirements`, `updateExileRemoval`, etc. (exported next to the reducer at the bottom of `draftSlice.js`).
- `collection` — which packs the user owns; saved in localStorage, and packs never seen before (new on ArkhamDB) start selected.

Slices import each other's actions and thunks directly (e.g. `dataSlice` imports from `settingsSlice`/`draftSlice`/`collectionSlice`), so watch for circular-import hazards when adding cross-slice code.

**Persistence (`src/storage.js`)** — guarded `loadJSON`/`saveJSON` over localStorage (it can be unavailable, so every call is wrapped). Keys: `draftham.theme`, `.collection`, `.collectionConfirmed`, `.cardsPerRow`, `.animationSpeed`, `.animateTogether`, `.scrollToTop` (the page scrolls to the top after a pick: `DraftPanel`, `InvestigatorPick`, and when the investigator draft screen opens; a switch in the settings menu, on by default), `.bannedCards`, `.savedDraft`. The pages must render fine when storage is empty or blocked.

**Undo and resume (`features/draftState.js`, `features/draftHistory.js`)** — both work on a snapshot `{ settings (without the preferences), draft, deckLoaded }`; the `restoreDraftState` action makes the settings, draft and data slices replace their state with it. `PREFERENCE_KEYS` lists the settings a restore must leave alone, so a new setting that is a preference (not part of the draft) has to be added there. Every pick (`draftCard` in `DrawDraft.js`) and "Done" pushes a snapshot onto an in-memory stack (`rememberUndoPoint`; `settings.undoDepth` mirrors its size for the UI), and the header's Undo button / Ctrl+Z pops it (`undoLastPick`). `store.js` autosaves the draft in progress to localStorage (debounced) and `components/ResumeDraft.js` offers to resume it on the setup screens (`resumeSavedDraft` re-applies the taboo list to the freshly fetched cards); only Discard, or leaving a complete draft through the header logo, clears the save. The first snapshot (the draft before its first pick, `getStartSnapshot`) is kept apart from the stack and saved with the draft: the header's Restart (`features/draftRestart.js`) restores it, deals new cards from a new seed, and can itself be undone; the logo instead leaves for the setup screens. Bump `SAVED_DRAFT_VERSION` when the shape of the saved state changes.

**Motion (`components/useMotionScale.js`, `data/AnimationSpeed.js`)** — the animation speed of the settings (and the system's reduced motion) reaches the CSS as `--motion-scale` on `<html>` (1 ÷ the speed multiplier, 0 when off), and the CSS animations of the setup steps (`.step-enter`), the investigator draft (`.investigator-deal`) and a newly chosen investigator (`.investigator-reveal`), the glow of the Draft List at the end of a draft, the cost curve and the transitions of the drawers, the dock and the hover states are written for 1× as `calc(0.5s * var(--motion-scale, 1))`, so they follow the slider (which is in the settings menu of every screen) and end at once when it is off; any new CSS animation should do the same and be disabled in the `prefers-reduced-motion` block at the end of `styles.css`. Animations started from code (`flyCard.js`, `returnCard.js`, `useFlipLayout.js`) take the multiplier from `motionSpeed(settings.animationSpeed)` or read `motionScale()`. `html` has `scrollbar-gutter: stable`, so a page that grows past the screen (the pack list of the collection panel) doesn't shift the layout when its scrollbar appears. Undo's reverse flight (`draft/returnCard.js`, the counterpart of `flyCard.js`) is prepared before `undoLastPick` is dispatched and lands on the `.draft-card-wrap[data-card-key]` of the restored pool; it works out which card the undo takes back by comparing the Draft List with the undo point (`peekUndo`), and does nothing when the list or the card is not on screen. Picking an investigator (`draft/flyInvestigator.js`) works the same way: the pick screen is copied and fades out, the front of the picked card flies to `#draft-left-panel .investigator-div` (on a phone or with the column in a drawer, it shrinks toward `[data-investigator-target]` / `.drawer-tab-left`), and while it flies `html` has the class `investigator-flight`, which fades in the panels of the draft screen (the pick screen has its own `key` in `ArkhamDraft.js` so that screen is a new element). Starting the draft from the setup does the same from the left column of the wizard (`startSetupFlight`), and Resume (`startResumeFlight`, no card: the screens cross-fade and the class `resume-flight` makes the investigator of the draft screen fade into place); leaving through the logo fades a copy of the screen away, and so do a pick that finishes the draft (`prepareCompletionExit`: the copy of the cards on the table is made before every pick and only put on the page if the draft turns out to be complete) and an undo out of the finished draft (`draft/screenTransitions.js`: copies are made before the state changes, and `copyOf` can put a copy in a box with a class like `draft-aside` so the column-scoped CSS still applies). Anything that has to stay on the page while it leaves (popups, dialogs, banners, the phone's confirm strip) is wrapped in `<Presence visible exit>` (`components/usePresence.js`): it keeps the last child with the class `is-leaving` for the exit time, and the CSS plays the exit; entering is a CSS animation of the element. The toggles (`.segmented`) get one sliding pill that `useSegmentedPills` places with a MutationObserver (no markup change in the components that have them), rows of a list that appear together cascade in (`row-enter`, decided in `CardListPanel`), and the panels of a paused upgrade draft rise in and fade away when the draft starts again (`phase-panel`, `playPanelsLeave`). Hovering is a soft ring (a glow of `--primary`, `--halo` in the block at the end of `styles.css`) that lights up around buttons, chips, segments, steps, switches, card lists, cards, investigator tiles and the knob of a slider, with no movement; a press shrinks the ring, the icon of an icon button swells a little and the redraw icon turns half a circle (`icon-redraw`); it only exists inside `@media (hover: hover)`. The theme change cross-fades through the class `theme-fade` that `setTheme` holds on `<html>`, the cost-modifier box of a card is always on the card and only hidden while closed (`.is-open`), and the cycles of the collection panel fold with a grid-rows transition.

**Seed and sharing (`random.js`, `share.js`)** — the draw uses `random()` from `random.js`, seeded with `settings.seed` when a draft starts (`useStartDraft`); the state of the sequence is part of the undo/resume snapshot. `share.js` builds and applies a link (`#setup=…`) that carries a build setup, its collection and the seed; `components/SharedSetup.js` offers it on the setup screens. Any new randomness in the draw must use `random()`, not `Math.random()`, or seeds stop reproducing drafts.

**Data cache (`cache.js`)** — the card, pack and taboo lists from ArkhamDB are kept in IndexedDB and never expire: a saved copy is always used (so the app starts at once and works offline), and the "Refresh card data" button in the header of the *Offline storage* panel of the collection panel (it also says when the data was fetched) clears the cache and reloads; the panel shows the cards, packs and taboo lists read-only and lets the languages and the card pictures be deleted and downloaded one by one. **When new content comes out (a pack, a taboo list, errata), raise `CACHE_VERSION` in `dataSlice.js`**: users then fetch the new data the next time the page loads, and the copies of older versions are deleted.

**Interface language (`src/i18n/`)** — every text the user reads goes through `t()`: `const t = useT()` in components (it also re-renders them when the language changes), the plain `t` from `i18n/index.js` in helpers (called at render time, never at module load). The English text is the key and must be a string literal (`t('Start draft')`); `{name}` marks values, `a|b` plural forms (`t('{count} card|{count} cards', { count })`); a table of texts kept until display uses `msg('Text')` and `t(item.label)`. Dictionaries are `src/i18n/locales/<code>.json` (`de es fr it pl pt ko ru uk zh`, loaded lazily with `import.meta.glob`), plural forms written in the order given by `pluralForms()` (Korean and Chinese have a single form). A text with no translation shows in English. **When you add or change a text**: wrap it in `t()`, run `node scripts/i18n-catalog.mjs` (rewrites `src/i18n/catalog.json`, the list of all texts) and add it to every locale file — `npx vitest run src/i18n/locales.test.js` fails until all ten are complete, have the same `{placeholders}` and the right number of plural forms, and contain no unused texts. The first translations were written without a native review (the terminology of each language's edition of the game comes from memory or from ArkhamDB's translated card texts), so wording corrections from native speakers are welcome. Dates are written with `formatDate`/`useFormatDate` (the language chosen, not the browser's), never `toLocaleDateString(undefined, …)`. The exported `.o8d`/`.txt` files and everything keyed on card names stay English.

**Card languages (`data/Languages.js`, `components/useCardName.js`)** — the card data (and all the logic keyed on card names) stays English. The language chosen in the header (`settings.language`, saved in localStorage; it also sets the interface language) makes `fetchTranslations` fetch that language's card list and pack list from ArkhamDB's translated site (`<code>.arkhamdb.com`), keep only `{ name, subname, customization text }` per card code (plus `text`, `traits`, `flavor` and `back`, the back text, for the cards that have a translation) and the name per pack code, and cache them like the other lists (`names-<code>` and `pack-names-<code>` keys). The investigator-expansion suffix of the pack names differs in each language and is cut by `EXPANSION_SUFFIX` in `Languages.js` (add a language there too). What the user reads about a card or a pack goes through `useCardName()` (`cardName`, `cardSubname`, `compareNames`, `customizationText`, `cardTexts`, `packName`), which falls back to the English text; names stored or sent elsewhere (ban list, `.o8d` export) stay English. The card images are always English: ArkhamDB's translated sites serve the same pictures. Because of that, in every language but English, the picture of a card gets the translated texts printed over the English ones: `CardTextOverlay.js` is placed right after an `img` (the hover preview, the cards of the draft, `CardImage` and the bonded cards) and paints over the rules text area and the one-line fields (name, subtitle, type, kind of weakness) with the text of the language chosen. Where those areas are on each kind of card (assets, events, skills, weakness treacheries and enemies, both sides of the investigators), measured on the pictures, is in `data/CardTextBox.js`; the type names of each language are in `data/CardTypeNames.js` (ArkhamDB gives them in English only); on the back of an investigator the text goes around the photo, whose measures (found by analysing the pictures) are in `data/InvestigatorPhotos.js` and need a line when a new investigator comes out; the text shrinks until it fits. The overlay follows the picture as it is drawn (a picture fitted inside a bigger box is measured by its drawn size), and the big preview turns an investigator's portrait picture a quarter (`OverlayCardImage`, `rotate`: front clockwise, back counterclockwise) so cards always show horizontally; the overlay is then placed over the frame it is turned in. A field is left alone when the translation is the same as the English text, and a card with no known layout keeps its English picture and, in the hover preview, gets its texts in a panel beside it (`TextPanel` in `CardPreview.js`). `[icon]` tokens of the texts are drawn with the game's icon font (`assets/fonts/arkham-icons.woff`, copied from ArkhamDB, which doesn't allow other sites to load it; the glyphs are listed in `data/CardIcons.js`) and the classes as colored dots. A new place that shows a card name should use `useCardName` too.

**Installable app (`vite-plugin-pwa`, `components/UpdateNotice.js`, `components/InstallButton.js`)** — `vite.config.js` generates the web manifest and a Workbox service worker (app shell precached, Google Fonts runtime-cached; card images and ArkhamDB data are not, the data lives in the IndexedDB cache). `registerType` is `prompt`: a new version waits until the user clicks Reload in `UpdateNotice`, so a draft is never interrupted. The service worker is only active in production builds (`npm run build` + `npm run preview`). The manifest has the full name as `short_name` (it is the label under the icon). `install.js` catches the browser's `beforeinstallprompt` at startup, and `InstallButton` (next to the settings button, in `SettingsMenu`) is a download icon with a tooltip that says why to install: it opens the browser's install dialog, or the tooltip gives the steps (Safari on iOS, or after the dialog was closed); it stays until the app is installed and is not shown inside it. The card pictures seen are also kept in the Cache Storage `card-images`: by the service worker (a runtime route; it only works in the published app, and only once the newest version is in charge) and by the page itself (`startRememberingImages` in `imageCache.js`, started in `index.js`: every card picture that loads is put in the cache, a few at a time, so the count doesn't depend on the service worker; the answers are opaque because the image sites send no CORS headers, so they can be counted but not measured: the *Card images* row shows an estimate of the room they take, `estimateImageBytes` in `imageCache.js`, the number of saved pictures times the average size of a picture of each site), and the collection panel has an *Offline storage* panel (`components/wizard/CachePanel.js`, `imageCache.js`, `savedCopyRows` in `dataSlice.js`) that lists what is saved (cards, packs, taboo lists, the names in every language, the pictures of the collection) with a Delete and a Download-missing button for each. A new kind of saved data needs a row there.

**Draft engine (`src/draft/`, `src/data/`)**
- `data/CardFilter.js` — the core eligibility logic: given investigator deck options, selected classes/traits, collection, taboo, ban list and phase, returns the set of legal cards (also `filteredCount`, `filterResearch`, `extraDeckRequirements`, draft weighting). Largest and most rules-heavy file; investigator-specific deckbuilding quirks live here.
- `draft/Sealed.js` — the **Sealed** alternative to drafting, for a new deck, the upgrades and the small drafts that come with them (the bonus XP of a new deck, the level 0 replacements, Versatile: `SEALED_SMALL_PHASES`, whose panels show `SealedExtraSetting` instead of "Cards to select from"; the setting is `settings.deckbuilding`, `draft` or `sealed`, next to `sealedExtra` (the cards dealt over the ones to pick, in percent: 0 to 500, +100% by default), `sealedPhaseExtra` (the own percentage of a small phase) and `sealedCopies`). `isSealedDraft(deckbuilding, phase)` is true in the build phase of a sealed deck: `fillDraft` then deals the whole pool at once (`SealedDraft` in `DrawDraft.js`: a partial shuffle of the legal cards with `random()`, every card face up, shown by class and name) instead of a batch, a pick adds one copy, or the myriad count of the setting for a myriad card (the same option as the draft), and `testForAdvance` takes no new cards: `trimSealedPool` removes from the pool the cards the deck can no longer take (two copies, or one, or no longer legal for the investigator, by running the draft filter again). `DraftPanel` keeps the pool on the table (no redraw, no scrolling to the top, the state of the pictures follows the cards that are left) and shows the copies already in the deck on a card; The size of a pool is `sealedPoolSize`: the cards left to pick (the deck size, what is left of the replacements or of Versatile; for the phases in XP, the experience left over the mean cost of the cards by their weights, `expectedPicks`) with the percentage over them, shown next to the slider (`useSealedPoolSize`); the replacements and Versatile ask for different cards as they go, so `trimSealedPool` deals new cards into their pool when it has fewer than the percentage says. In an upgrade (`UpgradePhase`; `isSealedBuild` is the build only) the pool is level 1+ cards that cost no more than the experience to spend, dealt by the weighting of the setup; after every pick `trimSealedPool` drops the cards that cost more than what is left and prices the others again (`repricedPoolCard`: the upgrade chosen on a card stays when it is still offered), the copies are the ones picked from the pool, and the Draft List has no × (the replaced cards, the discounts and the exiles of an upgrade can't be taken back one card at a time: only Undo); the filters have a Level group when the pool has levels. A sealed deck needs a pool that can fill it (`sealedPoolFillsDeck`, checked in `useStartDraft`). The pool as it was dealt is kept in `draft.sealedPool` and `draftPool` is derived from it after every change of the deck, so a card that left the pool (two copies, or no longer legal) comes back when the deck changes back: `removeSealedCard` (the × of a row of the Draft List, `CardListPanel`) takes one copy out, undoes what the card did to the deck size, level 0 and build XP (not for `sealedCardRemovable` = false: Underworld Support, On Your Own, Shrewd Analysis and the research cards, which stay unless the pick is undone) and can be undone like a pick. The filters over the pool (`draft/SealedFilters.js` for the rules, `components/SealedFilterBar.js` for the UI; text, class, type, slot, cost, skill icons, trait, pack, as in ArkhamDB's search) only hide cards (`.is-filtered-out`, the cards stay in the page because the pick, the flight and the pictures go by the place of the card in the pool); the text, pack and icons come from ArkhamDB's version of the card (`state.data.cardData`), which the cards of the pool don't carry. With `sealedDuplicates` the pool is dealt with replacement (at most two of a card), each entry has a `poolId` (`sealedEntryId`; the pool and the image state go by it, not by the card code), a pick takes only that entry out (`draft.sealedTaken`) and the deck takes two copies of a card, so `sealedCopies` doesn't apply. The side columns of a sealed draft are sticky with their own scroll, and they have `scrollbar-gutter: stable`: without it the scrollbar coming and going changed the width of the column, and with it the height of the investigator's picture, so it came and went at every frame. `restoreSettings` fills in the sealed settings for a draft saved before the mode existed.
- `draft/DrawDraft.js` — (for a new deck, with `settings.proportionalLimits`, on by default: an investigator who can add only some cards through a deck option with a `limit`, like Zoey's 5 cards of other classes, gets them in proportion. `FilterCards` gives each legal card a `limitCategory`, the index of the limited option it is legal through, or null when it is legal without a limit; `proportionContext`/`categoryDraw` draw the category first, with the probability limit ÷ deck size (5/30), then a card of it, so a category with no cards left gives its share to the others; the sealed pool has exactly the share of its size, `categoryPlan`; a saved draft or a link from before it deals evenly) weighted random draw, `fillDraft`/`draftCard`/`redrawDraftCard`, simple draft vs the disabled "chaos" mode, XP/cost calculation (`costWithModifiers`, `calculateModifiedCost`), draft progress/target math, and `testForAdvance` which decides when to move to the next phase.
- **XP set aside** (`draft.xpSetAside`, said in the bar at the bottom of the draft screen, and by `XpSetAsideNote` on the screens after the draft): in the upgrade (`UpgradePhase` only) the experience that is not spent can be put aside for later. From a sealed pool `finishUpgrade` ends the upgrade at once with the picks so far and sets aside what is left; in the draft `skipUpgradeCards` takes nothing from the cards shown, sets aside 1 XP, lowers `settings.draftXP` by 1 and deals new cards (the upgrade ends when no experience is left). Both are undoable (an undo point is taken first) and have their buttons in the confirm bar next to Done, which only appears with a loaded ArkhamDB deck (it pauses the upgrade) or when no legal options are left.
- `draft/Modifiers.js` — "deck modifiers": cards in the deck that alter later drafting/costs (Arcane Research-style discounts, Versatile, etc.), added via `addDeckModifier` and applied via `addModifiers`/`availableUpgrades`.
- `draft/Level0.js` — counting of the level 0 cards still waiting to be drafted. `draft/ExportArkhamBuild.js` — export to arkham.build, which only imports ArkhamDB deck URLs and `.json` files in the shape of an ArkhamDB deck (`slots` as code → copies, `meta` a string of JSON with the choices of the deck creation under the ids of the deck options, `alternate_front/back` for a parallel investigator; the schema is `shared/src/schemas/deck.schema.ts` of its repository): `arkhamBuildDeck` makes a new deck (the button of `ExportPanel`, with the signature cards and the weakness), `arkhamBuildUpgradeDeck` the upgraded one (`UpgradeExportPanel`, on the paused and the complete screens of an upgrade: the deck as ArkhamDB gave it, kept in `draft.sourceDeck`, with the cards the draft ended with; it only exists for a deck loaded in this draft session, not for one resumed from a save made before `sourceDeck`). Card codes are used, so the 2026 cards that an .o8d can't carry are in it. `draft/ExportDeck.js` — export to ArkhamDB-compatible `.o8d` and plain text. ArkhamDB's .o8d import goes by the OCTGN id of each card, and its data has none for the newest content (the 2026 core and starter decks), so those cards are left out of the .o8d and listed in the export panel (`cardsMissingOctgnIds`); the text export, which goes by names, has them all (`textImportIssues` lists the cards its importer can't read, because it stops at a comma, a • or other special characters, and the weaknesses it can't tell apart; the export panel also lists the creation choices a file can't carry, like the classes of Charlie Kane). `draft/flyCard.js` — the "drafted card flies into the Draft List" animation.
- `data/DraftPhases.js` — phase enum (`AllCards`, `BuildPhase1-3`, `BuildUpgradePhase`, `UpgradeLevel0AddPhase`, `UpgradePhase`, `VersatilePhase`) plus `isUpgrade` / `isLevel0Upgrade` / `isLevel0Build` helpers used throughout both logic and UI. Note `UpgradeLevel0SwapPhase` is commented out in the enum but still referenced in the helpers. `data/PhaseLabel.js` gives the phase names shown in the header; `data/DraftModes.js` switches which draft types the UI offers (the engine still supports the disabled ones).
- `data/InvestigatorList.js` — the investigator list is **built from the card data** (`investigatorEntries`, hook `components/useInvestigatorEntries.js`), and the hook only gives the investigators that the **collection** has (`ownedInvestigatorEntries`: the pack of the card, or of a reprint of it such as the Revised Core Set, is selected; the list, Random and the investigator draft all use it). When the collection changes, `store.js` dispatches `dropInvestigatorOutsideCollection`, which drops an investigator chosen from the list that the new collection doesn't have (not one that comes with an ArkhamDB deck, and not during a draft): reprints and hidden cards are skipped, same-name versions become "Name (Parallel)" / "Name (Pack)", Agatha Crane has one entry per class. `data/RequiredCards.js` derives the cards an investigator always comes with from `deck_requirements` (used by the hover preview and the small pictures under the investigator).
- Packs: `data/PackCatalog.js` builds the collection groups from the ArkhamDB pack list and cards (new packs appear by themselves; each group has an `art` card, the first investigator of its first pack, whose picture is drawn dimmed behind the group in the collection panel, unless the group has box art (`data/BoxArt.js` maps pack codes to the pictures in `src/assets/boxes`, taken from the Fantasy Flight Games product pages, see `SOURCES.md` there; a new campaign needs a line there and a picture); each group has a `kind` when it isn't an expansion (`core`, `starter`, `promo`, `printplay`: the side stories of cycle 70 are merged with the standalone scenarios of cycle 90 into one *Print & Play* group, `MERGED_CYCLES`) and the groups of a chapter are ordered core sets, starter decks, then the cycles in release order; each group has a `chapter`: Chapter 2 is the 2026 core set and everything released from its date on, found from the pack list, so a cycle with packs of both is split, and the collection panel shows a heading for each chapter, with a note under Chapter 2 that ArkhamDB can't import its cards from .o8d files yet: delete the note when ArkhamDB has OCTGN ids for the 2026 content); `data/PackData.js` (pack code → name) and `data/CollectionGroups.js` are the built-in fallback used when ArkhamDB can't be reached. `data/ResearchLogs.js` — research-log card text.
- Card images: `data/CardImages.js` (`cardImageUrls(card, side)` tries the arkham.build CDN first, 750×1050 WebP, then ArkhamDB's 300×419 PNG for the cards it lacks), used by `CardImage`, `OverlayCardImage` and `CardPreview`.

**UI (`src/components/`)** — `ArkhamDraft.js` is the top-level switch between the setup wizard, the investigator draft, the drafting screen and the complete screen. The known-issues comment at its top lists existing limitations (parallel investigator export, Myriad at level 0).
- *Setup wizard* (`SetupWizard.js`, `components/wizard/`): breadcrumb steps Investigator (pick from the list, random, or investigator draft) → Deckbuilding Rules (Build or Upgrade, how the cards come (Draft or Sealed), rules, deck options, deck import) → Review. The collection (packs, taboo list, ban list, *Offline storage*: `CollectionStep`) is not a step but a sheet, `components/CollectionDialog.js`, drawn in `document.body` and open while `settings.collectionOpen`: it opens by itself on the first visit (`collectionConfirmed` is false), after that from the first row of the settings menu on the setup screens (`SettingsMenu`'s `onCollection`) and from the Edit buttons of the review; what the collection comes to is told by kind of product (`data/CollectionSummary.js`, `components/CollectionRecap.js`): for each chapter, a row per kind with how much is selected ("Core Set 1/1", "Starter Decks 5/5", "Expansions 10/10", "Return to Boxes", "Promos", "Print & Play": expansions are counted by campaign and the rest by pack; the second copy of the core set isn't counted), in the *Your setup* column and the review, not in the panel (its list says it already) and not on the settings row, which is only the button; Done, Escape and the backdrop close it, and `confirmCollection` (also dispatched when a draft starts or a shared setup is applied) marks the collection confirmed and closes it. `settings.setupStep` drives the steps; no investigator is chosen when the page opens (`settings.investigatorData` is null until one is picked from the list, drafted or taken from an ArkhamDB deck: the left column shows none, the Continue and Start buttons wait for one, and any setup code that reads it has to cope with null); a redraft returns to the Investigator step. `describeSetup.js` has the plain-text summaries shared by the summary column, stepper and review.
- *Draft screens* have breadcrumbs in the top bar (`DraftBreadcrumbs`: Setup, which does what the logo does; the investigator draft, when the setup has one, which after a confirmation (`ConfirmDialog`, also what `RestartDialog` is made of) drops the deck draft and deals new investigators, `backToInvestigatorDraft` in `features/draftRestart.js`, which puts the deck draft aside with its undo points (`leaveDraft` in `draftState.js`) so that Undo, on the investigator draft, brings it back (`undoBackToInvestigators`); picking another investigator lets it go; and the phase, which is where you are). They share one layout (`.draft-layout` with `.draft-left` / `.draft-main` / `.draft-aside`): `DeckSidebar.js` (`DeckLeftColumn`, `DeckRightColumn`: investigator, deck lists, cost curve, upgrade/deck options), `DraftPanel.js` (the card pool, with the flip, redraw (one card, or all of them with *Redraw all*, a button that `DraftPanel` and `InvestigatorPick` draw into the slot of the top bar after the breadcrumbs (`#draft-header-slot`), or, on a phone, in a row above the cards; the confirm bar under the cards only has the progress and Done and the investigator draft has none, a card or an investigator is picked with two clicks) and fly animations), `CardListPanel`, `ExportPanel`, `UpgradeOptionsPanel`, `Level0UpgradePanel`, `VersatilePanel`. When the draft completes the panels re-arrange into a grid of columns (the investigator and cost curve, the export and other panels, the Draft List with the removed cards, the Deck List: `DeckRightColumn` with `split`; a column with nothing in it is dropped) and `useFlipLayout.js` animates the move. Below 1380px the side columns become drawers (on a phone, see *Phone layout*).
- *Hover previews*: every image hover goes through `useCardOverlay` (`OverlayImage.js`; a hover opens the preview once the pointer has settled on the card for `HOVER_DELAY` (200 ms; moving more than a few pixels starts the wait again), so sweeping over the cards shows nothing, and only when the pointer really moves: a card that appears under a resting pointer, on a new screen, after a redraw or a pick, waits until the pointer has moved a few pixels over it; keyboard focus, a tap and the Zoom button open it at once), which stores the image, anchor and card code in `settings`; `CardPreview.js` places the big preview beside the hovered element, with bonded cards (one or two at 80% of the card; three or more, like the research families, in a row that scrolls sideways with the mouse wheel while the preview is shown, `BondedStrip`; and, for a card of a research family such as Strange Solution or Forbidden Tome, the other cards of the family, found by name in `data/ResearchCards.js` because ArkhamDB doesn't link them) and customizations, scaling down to stay on screen. On touch screens there is no hover: `useCardOverlay` opens the preview after a long press, "pinned" (`settings.imagepinned`): `PinnedPreview` in `CardPreview.js` is a scrolling layer with the card as large as the screen allows and its bonded cards and customizations under (or beside) it, inside a backdrop that closes it when tapped, and swallows the click that ends the press so the card isn't selected or drafted. Things a tap does nothing else on (the rows of the card lists, the investigator pictures, the required-card thumbnails) pass their click event as well, on touch screens only (`isTouchScreen()`), and the preview opens at once.
- *Phone layout* (`components/usePhoneLayout.js`): a phone is `PHONE_QUERY` (max-width 700px, or a short landscape screen that can't hover). `usePhoneLayout()` gives that as a boolean, `ArkhamDraft` puts `.is-phone` on `.App`, and the components that only exist on a phone are rendered only then, so a PC keeps exactly its own layout (compare layout geometry at 1920/1440/1381/1380/1100/901/701px before and after a change that touches shared code). New phone CSS goes in the "phone layout" block at the end of `styles.css`, under `.is-phone` or on classes that only the phone components have; the drawers and edge tabs (`DrawerControls`) stay for tablets and narrow desktop windows. On a phone: `AppHeader` is a short sticky top bar (logo, breadcrumbs: only Setup and the phase, which ends in an ellipsis before it reaches the count, and the way back to the investigator draft is a row of the settings menu then, `useDraftProgress` count and thin progress line, settings; Restart is in the settings menu through `RestartDialog`, Undo in the dock, or in the bar on screens without a dock); `PhoneDock` (investigator, Undo, card lists with a count) and `DeckSheet` (the two columns as the tabs of one sheet, a `.segmented` toggle like the investigator step's, which also changes tab with a sideways swipe on the lists: left for the card lists, right to go back, and on a landscape phone a swipe to the right on the card lists goes back to the first tab before it closes the sheet; closed by the X, the scrim, a swipe (down from the top of the sheet, or from anywhere on it while the lists are scrolled to the top), Escape or the back gesture: `ArkhamDraft` adds a history entry while a drawer is open) replace the drawers, and in landscape the dock is a column on the right and the sheet comes in from that edge; `DraftPanel` shows each card with a Redraw / Zoom row under it (`.draft-tile`), a chip with the XP cost that opens the cost modifiers in a sheet (`modifierParts`, shared with the PC's box). The PC's small XP box and the phone's chip are pills drawn over the level pips under the card's cost (the arc of dots in the cost circle); on a PC hovering the pill opens a small box with the modifiers at the bottom of the card, which stays open while the pointer is on the pill or on the box and closes 150 ms after it leaves both (a click holds it open until the next click); every card (`.draft-card-wrap`) is a size container so their size and place follow the width of the card (`cqw`, with percentages as the fallback), and instead of the confirm bar a strip above the dock that exists only while a card is selected (or a Done button); `SetupWizard` has a one-line top bar (`Step n of 3`, tapping it opens the list of steps; a sideways swipe on the page goes to the next or the previous step, `components/useSwipe.js`, held back like Continue is while there is no investigator) and a sticky bottom bar whose primary button is Start draft on the last step; `InvestigatorPick` shows each investigator compactly (name, front, the required cards as thumbnails that open in the preview when tapped, then Redraw / Front / Back side; the back opens in the preview) with the same confirm strip, without a dock. The older panels of the draft screens (Level 0, Versatile, bonus experience, the paused upgrade: `.fbsetting` rows, `.button-rect`) are dressed like the rest of the app on every screen size (label and control per row, 16px fields and 44px rows, which iOS needs so that it doesn't zoom the page) by the "older panels" rules under `.draft-main .settingsDiv` at the end of `styles.css`, without changing their markup. `useScrollLock` keeps the page from scrolling behind an open sheet. The card that is drafted flies to `[data-fly-target]` (the dock's card lists button) or, on a PC, to `.drawer-tab-right`. Needs `viewport-fit=cover` (in `index.html`) and `env(safe-area-inset-*)` for the notch and the home indicator; heights that follow the visible screen use `dvh`.
- Legacy setup components still used by the wizard's rules step: `Build*Settings`, `Upgrade*Settings`, `PhasedDraftSettings`, `PhaseSettings`, `DeckOptionsPanel`, `BuildUpgradePanel`.

**Styling** — one stylesheet, `src/styles.css`, imported by `index.js`; it has three sections in cascade order: page basics, layout and draft cards (older rules, still needed) and themes and components (design tokens and the component classes of the redesign). Themes (`light`, `dark`, `arkham`, `innsmouth`; the switch in `ThemeToggle.js` shows each with an icon, the Arkham one the auto-fail tentacle and the Innsmouth one the Elder Sign, both outlines taken from the arkham-icons font) are set with `data-theme` on `<html>` by `theme.js`; colors come from CSS variables (`--bg --surface --text --primary --line …`, defined per theme in the last section of `styles.css`), so new CSS should use the tokens, not fixed colors. Prefer the shared classes (`.panel .btn .btn-primary .field .setting-row .options-section .check-row .switch .chip …`) over adding new ones. Every slider is a `SegmentedRange` (`components/SegmentedRange.js`, never a bare `<input type="range">`): the wrapper draws one segment per step and fills them up to the knob (more than 20 steps: one continuous bar), and the sizing rules of a slider go on `.segmented-range`, not on the input inside. Before deleting a class, grep for it in `src/**/*.js`: some are built from pieces (e.g. `'rotated-' + side`).

## Adding game content

Most new investigators and packs now show up by themselves (investigator list and collection groups are derived from ArkhamDB). Special-case cards and investigators with unusual deckbuilding rules still need hand-written handling in `CardFilter.js` / `Modifiers.js` (by card name or code), and, for the signature cards of the export, in `ExportPanel.js` (Lily Chen, Occult Evidence, Burden of Destiny) and `RequiredCards.js`. Grep for an existing investigator or card name to find every place that needs a matching change; recent commits ("added new expansions with same name character logic", "Suzi/Parallel Pete, fixes", "The Drowned City") show the pattern.
